# 開封台帳 運用手順書（解析依頼者・解析実行者向け）

作成日: 2026-11-04 / 対象: 製造データ解析を判定器（validity engine / judge_gate）に通すすべての解析

関連: 判定器まわりの恒久対策（データ開封台帳・独立性検査・判定票）。本書は運用手順のみを定める。
実装の規約は `relay/judge_gate.py` のモジュール docstring（「やること」(i)(ii)(iii)）に従う。

---

## 0. なぜこの手順が要るか（背景）

ロスの解析（`時間分割確認_20261103/ロス/mcl_loss_ftype_confirm`）で、判定器は `order_ok=true` と GO を
返したが、実体は採用に値しなかった。原因は 2 点:

1. **確認用データが独立でない** — 確認に使ったロットが、前の解析で既に開封（DB から取得）済みの
   期間に含まれていた。`order_ok` は「登録時刻がデータ取得時刻より先」という**時計の前後だけ**の見かけで、
   「そのロットを以前に誰も見ていない」ことは保証していなかった。
2. **比較が製品（塗工布品名）をそろえていない** — 曝露の群ごとに品名が偏っていた（別担当 confound_gate の設計検査で扱う）。

この手順書は **(1) 独立性** を運用で守るためのもの。鍵は 1 つ:

> **確認用データの取得（fetch）は、主張の登録（register）より後にのみ行う。**
> 登録より前に取得・開封されたロットは、確認には使えない（独立でない）。

## 2. 解析を依頼するときの手順

### 2-1. 台帳への記録は自動で行われる（依頼者が手で書かない）

解析が DB からロットを取得するたびに、ハーネスが台帳へ 1 行を追記する。依頼者・実行者が手作業で
台帳を編集することはない。台帳を手で書き換えると独立性検査の前提が崩れるので、**編集しないこと。**

記録される三段階（`judge_gate.py` の「やること」）:

1. **(i) record_manifest** — 解析結果と入力データの sha256、取得時刻を記録。
2. **(ii) register_and_lock** — 主張を登録してロックし、登録時刻と取得時刻の**前後**を記録。
3. **(iii) run_engine_judge + build_judge_footer** — 判定器を回し、判定票に結果を載せる。

このとき、取得したロット集合が台帳（`data_access_ledger.jsonl`）に追記される。

### 2-2. 確認用データの取得は「登録の後」にだけ行う（最重要）

確認解析（前向き確認）を依頼するときは、順序を必ず守る:

1. 先に、検証したい主張を **登録・ロック**する（register_and_lock）。
2. **その後で**、確認用データを DB から取得する。
3. 取得した確認用ロットは、登録時刻より後に初めて開封されたものだけが独立。

**やってはいけないこと**: 先に確認用データを手元に取ってから主張を登録する。これだと「登録より前に
開封済み」になり、独立性検査で保留になる（下の §3）。

### 2-3. 確認用は、製品（塗工布品名）をそろえる

曝露の群どうしで塗工布品名がそろうように確認用データを選ぶ。品名が偏ると、設計検査（confound_gate）で
「層別列の有無・群ごとの品名の偏り」が判定票に記録され、採用の妨げになる。確認用の抽出条件に品名を明示する。

---

## 3. 独立性検査で「保留」になったときの読み方

確認用の判定で judge_gate が独立性検査を行う。確認用データのロット（曝露と結果の組ごと）のうち、
台帳で「**登録時刻より前に別の解析が開封した**」ロットの割合を計算する。

- 割合が **0 より大きい** → 判定票に「**確認用データは開封済み（独立でない）**」と明記され、
  `order_ok` は **false** に落ちる。判定器の出力が GO でも、ハーネス側の最終表示は
  **採用ではなく「保留」** になる（判定器の元の出力は変更せず残す）。
- 割合が **0** → 独立。GO はそのまま GO として通る。

**保留が出たときの対処**:

1. どのロットが開封済みかを台帳で確認する（`fetched_at` が確認用の `registered_at` より前の行）。
2. 開封済みロットを除いた、未開封のロットだけで確認用データを取り直す。
3. **必ず登録の後に取得する**（§2-2）。
4. 製品（品名）をそろえ直す（§2-3）。

**保留は正しい挙動**。緩めない。判定器の基準・Δmin・補正は変えない。

---

## 4. 判定票（footer）の読み方

判定票には以下が載る:

- 判定器の verdict と理由コード、区間、n。
- 独立性: 開封済み割合が 0 より大きければ「確認用データは開封済み（独立でない）」。
- 設計検査（confound_gate）: 層別列の有無、曝露の群ごとの品名の偏り。
- **ERROR の扱い**: ERROR は**未解析**であり、判定として数えない・NA に丸めない。
  入力の誤りで ERROR になったときは、判定器のメッセージがそのまま担当に返る。

判定器が回せなかったときは、判定票にその**理由**が必ず出る（黙って消えない）。

## 6. やってはいけないこと（禁止）

- 判定を緩める変更（基準・Δmin・補正の変更）。
- 台帳の手編集・取得順序の逆転（確認用を先に取る）。
- ERROR を判定に数える / NA に丸める。
- 保留を無視して採用する。
