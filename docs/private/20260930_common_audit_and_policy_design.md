# Common audit events, lane policy, credential placeholders, executable pinning (design)

Status: design only, nothing implemented, no product file touched. Date 2026-09-30. Base: origin/main 76e0bdb. File:line references are to that tree unless marked (live), which means the live checkout was read (read-only). Ideas come from a read-only study of NVIDIA OpenShell (Apache-2.0); no code was copied. Tags: [M] measured, [V] verified by reading code, [A] assumed, [U] unknown.

## 0. Friction budget (binding on everything below)

The owner's worry is inconvenience. These limits are acceptance criteria for every PR in section 6; a PR that misses one is not merged.

| # | Limit | Value |
|---|---|---|
| F1 | New prompts, gates, toasts or notifications to the owner | 0, in every mode. Bypass (`job_approval_mode=bypass`) never asks through any channel for any gate type; the new code has no "ask" outcome at all (the event vocabulary keeps `ask` only to describe the EXISTING gates). Shadow findings are files and a cockpit list the owner opens by choice, never a popup. |
| F2 | Added latency per audited action | p50 <= 2 ms, p95 <= 5 ms, and the writer never waits on a lock (try once, drop and count). Baseline [M, 100 runs each, this machine, 2026-09-30]: `tool_ledger._append` p50 11.2 ms / p95 13.9 ms, of which `redact_secrets` alone is p50 8.7 ms / p95 20.7 ms because it re-reads `.env` and re-decrypts DPAPI on every call (`secret_store.py:228-262`); a bare open-append-close is p50 1.1 ms / p95 2.0 ms. `record_bypass_decision` (`approval_policy.py:90`), `lock_state._append_log` (`:118`) and `SocketRoute.record` (`socket_route.py:179`) are bare appends with no redaction, about 1 ms. So the budget is met only if the audit path redacts from a cached secret list (keyed on `.env` mtime+size and an env fingerprint), not by calling `redact_secrets` per event. |
| F3 | New required setup step | None. The audit file and the pin store are created lazily; absent policy file = today's behaviour; nothing in quickstart.bat/start_all.bat changes; no admin, no optional Windows feature, standard user. |
| F4 | Storage growth | Hard cap by construction: one 4 MiB fixed-size ring (8192 slots x 512 B), preallocated once. Measured decision volume is about 1,000 events/day [M, section 1], so the ring holds roughly 8 days. Policy file < 64 KB. Pin store <= 2,000 entries (< 256 KB). A full disk cannot make any of it fatal: ring writes overwrite existing bytes (no new cluster is needed), every write is try/except, failures are counted (same reasoning as the free-space ring in `20260930_fleet_interrupted_resume_design.md` section 3: 256 x 128 B slots, handle kept open, `write` failures swallowed and counted). Nothing here reads or proposes a disk-floor value. |
| F5 | Enforcement default | Every enforcement is `off` or `shadow` by default. Shadow computes the decision and writes `would_deny` plus a per-lane per-day counter; it changes no behaviour. Only the owner turns anything to `on`, and only through the GUI (same pattern as `effort_policy=off\|shadow\|on`: settings key, env override, `mode_info()` shows the source; the cockpit control rides after the other engineer's ui/ commits). Item 1 records only (no decision is altered), so it is the one thing that starts `on`. |
| F6 | Rollback | One setting per item returns to today's behaviour with no restart (`audit_mode`, `lane_policy_mode`, `exec_pin_mode`, `secret_broker_mode` = `off`); deleting the item's data file does the same. The writers keep their existing files and consumers, so removing the adapter deletes nothing anyone reads. |
| F7 | Promotion rule | A feature that produced more than N = 3 false `would_deny` per lane per day in shadow (median over the shadow window, false = the action was later needed for a run that finished DONE, or the owner marked it benign) is not promoted; it is fixed or dropped. Minimum shadow window 14 days with at least one fleet run per day; zero shadow events is "not yet measurable", not "safe". |

## 2. Item 1: common audit event

Event (one JSON line, <= 512 bytes after truncation): `v` (schema_version, 1), `ts`, `actor` (lane or component: `fleet:w3`, `mcp:<client_id>`, `child:python`, `supervisor`), `action` (dotted verb: `gate.ask`, `unlock.refuse`, `auth.reject`, `route.fallback`, `exec.launch`, `secret.resolve`), `target` (short, path/tool/host, truncated 120), `decision` in `allow|deny|ask|bypass|would_deny|error`, `reason` (<= 160), `policy_id` (item 2's id or empty), `run_id`, `instance`, `turn`, `corr` (correlation id: the tool_ledger call id when one exists, else a random 8 hex), `evidence_ref` (`file#row-or-sha16` pointer to the richer legacy row, never a copy of it). Goal text and command text are never copied: hash (sha16) plus length only, because socket_route rows already carry goal text under a gitignore-only protection.

Redaction: every string field passes through a cached secret list built by `tools.secret_store.secret_values()` (values, not names) and refreshed only when `.env` mtime/size or the env fingerprint changes; the module calls the existing `secret_values`/`REDACTION_MARKER` unchanged. Failure to build the list fails closed exactly like `redact_secrets`: the event is written with `reason` only and `[redaction failed]`, never raw. The cache keeps the 2 ms budget (F2) that per-event `redact_secrets` (8.7 ms) would break.

Adapter: a pure module `tools/audit_event.py` (new, not frozen) with `emit(action, decision, **kw) -> None`. Existing writers call it additively after their own write, inside their own `try/except`, so nothing existing changes (their files, schemas, readers stay). Call sites in phase 1, all non-frozen: `approval_policy.record_bypass_decision` (decision `bypass`), `lock_state.record_locked/record_granted` (`deny`/`allow`; this is how unlock decisions are covered WITHOUT editing frozen `tools/security.py`), `auth_stats.record_rejection` (`deny`), `gate_ops` ask path (`ask`), `tool_ledger.record_outcome` only for refusals (`looks_refused`), not every call. Frozen: `relay/socket_route.py` cannot be edited; propose `relay/audited_socket_route.py` (subclass overriding `record`, calling super then `emit`), swapped in at `relay_fleet.py:1926` (one line, conflict-prone), or as the zero-touch alternative a read-only follower that tails `socket_route.jsonl` and emits pointer events. `relay/selfimprove/authority_ledger.py` (frozen, hash-chained) is NOT written into and NOT wired in phase 1; wiring its `append` would need the owner's explicit authorization and baseline re-signing; a read-only follower using its public `read()/tail()` could emit `evidence_ref="authority#<seq>:<hash16>"`.

Safe writing: one preallocated ring file `.fleet/audit.jsonl` of 8192 slots x 512 B, each slot a JSON line space-padded to 511 bytes plus `\n` (valid JSONL, so `ledger_health` and every jsonl reader work unchanged). Slot index from a counter in a 16-byte header guarded by a non-blocking `msvcrt.locking` byte lock (one attempt; on failure use `(pid, seq)` hashed slot; on any error drop and count `audit_dropped`). Multiple processes (server, relay, bridge) may write; overwrite within file size allocates nothing. Never raises into the caller. Counters (`written`, `dropped`, `ms_p50/p95`) go to a small `.fleet/audit_stats.json` snapshot (atomic tmp+replace, same as `auth_stats.write_snapshot`). Mode key `audit_mode=on|off`, default `on`.

Tests (PR-1): schema round-trip and truncation to 512 B; a secret present in env/`.env` never appears in the slot (extends the shape of `tools/test_ledger_never_writes_a_secret.py`); `emit` never raises with a read-only dir, ENOSPC, corrupt header, and lock contention; ring stays 4 MiB after 20,000 emits; two-process concurrent emit loses none within one lap; p50 <= 2 ms benchmark script (reported, not a flaky CI gate; CI asserts <= 25 ms); each dual-write call site: the legacy file's bytes are identical with the adapter on and off; conftest redirect entry plus the isolation test; no `audit_*` field is empty on all rows (else `KNOWN_EMPTY` with reason). Cockpit reading is a later pointer only: a read-only `scripts/audit_tail.py` and a list in the health strip; not designed here.

## 3. Item 2: per-lane policy file

What a lane is here (mapped to existing concepts, [V]): (a) a fleet worker/run (`w0..wN`, fan-out children; identity is `worker`/`run_id`, not the caller IP, since the tunnel makes every IP local); (b) an MCP client identity: `folder_policy.current_scope()` = authenticated `client_id` (`folder_policy.py:112`), today collapsing to "global" because there is one shared token; (c) child processes of `run_python`/`shell`/jobs (`code_exec.py:110,389`, `shell_extra.py:174,271`, `jobs.py:210,262`), which already get `sanitized_child_env()` (`_subproc.py:93`, secrets stripped by name and by URL-userinfo value); (d) a bench arm (companionbench runner / `bench/*` arms). Existing per-lane knobs today: `MCP_ALLOWED_BASE` and `.fleet/folder_access.json` (per-scope roots, default-open, tolerant of unknown keys, `folder_policy.py:20-31`), `job_approval_mode` (global, settings.txt), the tool catalogue's unlock classes, `command_judge`.

Format: JSON, stdlib only. `import yaml` works in the venv (PyYAML is in requirements.txt:20) but YAML brings implicit typing (yes/no, octal), duplicate keys accepted silently and a second dependency surface for a file the owner will rarely hand-edit; TOML is unavailable (Python 3.10.0, no `tomllib`). Loader uses `object_pairs_hook` to reject duplicate keys. Location `.fleet/lane_policy.json` (gitignored, per install), re-read on mtime like `folder_policy`.

Strictness: unknown field at any level = the whole file is rejected (not partially applied), an `error` audit event `policy.load` is written with the field path, and the effective policy stays the built-in default. That is deliberately the same direction as `folder_policy` ("a policy file that cannot be read must never lock the tools down"): rejection falls back to today's behaviour, never to "deny all". `schema_version` is required; a newer version than the code knows is rejected the same way; older versions get an explicit migration function tested against golden files.

Migration rule "the default policy reproduces today's behaviour exactly": the built-in default has every mode `off`. A golden-equivalence test drives a matrix of (scope, path, mode) inputs through `folder_policy.allowed_bases`, `approval_policy.current_approval_mode`, `_subproc.sanitized_child_env` and asserts the lane-policy evaluator with the default gives identical results, and that with the default loaded no existing function's result changes (the module is not on any decision path while `lane_policy_mode=off`).

Proof that a declared field takes effect (extends the repo's rule from `test_a_declared_field_is_a_written_field.py`, which is about ledger columns): every field in the schema table needs (1) a reader in non-test source found by AST scan of the evaluator (a field nobody reads fails), (2) a flip test where changing only that field changes the evaluator's decision, and (3) in shadow, `policy_id` non-empty on every `would_deny` row (checked by the existing ledger_health mechanism on `.fleet/audit.jsonl`).

Frozen interactions: `tools/folder_policy.py` is frozen, so item 2 never edits it: phase 1 only READS `describe()/allowed_bases()` and compares with the lane's declared roots to emit `would_deny`; enforcement later means generating the `.fleet/folder_access.json` data file that `folder_policy` already consumes (a data write, no frozen source change; owner turns it on in the GUI). `tools/security.py` and `docs/SECURITY.md` stay untouched; documenting the feature in SECURITY.md needs the owner's explicit authorization (design text lives here). `bench/companionbench` core is not edited: an arm policy is a data file read by a new non-core `bench/lane_arm.py`.

Proposals, never auto-applied: `scripts/lane_policy_propose.py` reads shadow `would_deny` events and writes `.fleet/lane_policy.proposed.json` plus a plain diff; adopting means the owner pressing a GUI control that copies it over; no prompt, no toast, and under bypass nothing waits for anyone.

## 4. Item 3: credential placeholders

Secrets and flows [V]: `MCP_API_KEY` / `MCP_API_KEY_PROTECTED` (bearer for /mcp; read at main.py import through `secret_store.api_key_from_env`, `:114`; also sent by the ui bridge client); unlock password (`MCP_UNLOCK_PASSWORD[_PROTECTED]`, `unlock_password_local :193`, used by `relay_fleet.py:1347` and `copilot_bridge.py:6426` to inject the PLAINTEXT into the Copilot turn text, which is the flow where the model sees it; redaction is applied only when writing to disk); DPAPI store `secret_store.py:48-90` (user-bound `CryptProtectData`, no LOCAL_MACHINE flag); `.env` in the repo root; Copilot socket tokens captured in memory (`SocketRoute.token_for :264`); HF/other tokens in the environment. Not in scope: the internal GitLab token lives outside the product (owner's Desktop) and is not touched.

Where a placeholder could apply: (1) child processes: they already receive `sanitized_child_env()`, so today's answer to "children never hold secrets" is "strip"; a placeholder would only add a way for a child that LEGITIMATELY needs a token (a download needing HF_TOKEN) to use it without holding the value; (2) HTTP calls made by our own code for a lane (a helper adds an `Authorization` header from a name); (3) the unlock-password injection into chat text, where a placeholder gains nothing because the value must reach the far side literally.

Broker design without admin: in-process resolver first: `tools/secret_broker.py resolve(name, lane) -> str` reading the same sources as `secret_store` (env, `.env`, DPAPI) at use time; per-lane allow-list of NAMES from the lane policy (`secrets.allow`, default empty); every resolution emits `secret.resolve` with name, lane and decision, never the value. Children get `{{secret:NAME}}` in argv/env; a thin launcher wrapper (in `tools/childproc.py`, not frozen) substitutes at exec time, so the placeholder, not the value, appears in ledgers and process listings on our side. A loopback broker (127.0.0.1, random port, per-run token) is only needed for children that are third-party programs making their own HTTP calls; it would add a listener and a token to manage, so it is a later spike, not phase 1.

What it does NOT protect: any code running as the same Windows user can read `.env`, call `CryptUnprotectData`, or read the parent's memory, so a hostile child that is the same user can still get the secret; the broker prevents accidents (secrets in logs, in model context, in argv, in inherited env) and gives an audit trail, not confinement. The existing `sanitized_child_env` already covers the environment-inheritance accident [V], so the measurable gain is small today.

Benefit vs cost: benefit = (a) an audit event per secret use (currently zero), (b) removing the ability to want a secret in a child without a code change; unmeasured [U] how many children need one (none found in `code_exec`/`shell_extra`/`jobs` beyond stripped names). Cost = a resolver plus a launcher substitution, one more failure mode (a placeholder left unresolved reaches a child literally) and a new class of bug in `.bat`/PowerShell launchers. Verdict: build AFTER items 1 and 2 (it needs the lane allow-list and the audit event to be worth anything), and only if shadow data from item 1 shows a real secret-needing child. Smallest spike: `secret_broker.resolve` plus one lane and one consumer (an HF download helper), shadow only: log what `resolve` would have granted while the existing path still runs unchanged. Kill criterion: no consumer after 14 days of item 1 data means item 3 is dropped.

## 5. Item 4: TOFU executable pinning

Launch inventory [M, `tools.launch_sites.inventory()` over tracked Python at origin/main]: 82 subprocess sites: bench 51 (dev-only), scripts 16, tools 8, relay 7. It does not see PowerShell/`.bat` launches (supervisor.ps1, start_all.ps1, setup_devtunnel.ps1, heal_tunnel.ps1: 57/27/112/45 name hits of msedge/devtunnel/csc/wsl), so the inventory is incomplete for pinning by design. Product-relevant executables: `msedge.exe` (companion Edge, `edge_recover.py`, `start_companion_edge.ps1`), `powershell.exe`, the venv `python.exe`/`sys.executable`, `git.exe`, `devtunnel.exe` (already Authenticode-checked once at install, `setup_devtunnel.ps1:48,530`), `csc.exe` (UI build, `ui/rebuild_ui.ps1`, .NET Framework dir), `wsl.exe` (bench remote only).

Store: `.fleet/exec_pins.json`, atomic tmp+replace, `{schema, pins:{<lowercased full path>: {sha256, size, mtime_ns, signer, version, first_seen, last_seen}}}`, capped at 2,000 entries (oldest `last_seen` dropped). Hash cache key = (path, size, mtime_ns): an unchanged file is never re-hashed. [M] hashing msedge.exe (5.2 MB launcher stub) takes 180 ms cold, 17 ms warm; venv python.exe (237 KB) 21 ms. Note the finding: `msedge.exe` is a stub; the code lives in the versioned directory's DLLs, so a hash of the exe alone says little; pin exe hash plus `FileVersion` and record the versioned directory name.

Phase 1 behaviour: first use writes the pin and an `exec.pin_new` event (log only). A different hash writes `exec.pin_changed` with both hashes, sizes and signer, `decision=allow`; nothing is ever blocked in phase 1, and there is no prompt. Hook: `tools/childproc.py` (not frozen) `run`/`tree_popen_kwargs` call `exec_pin.observe(path)` inside try/except (budget: cache hit < 0.2 ms [A]); PowerShell-launched executables are observed by a once-per-supervisor-start `python -m tools.exec_pin --scan` invoked from `scripts/preflight.py` (assumed to run at start; not verified) rather than editing supervisor.ps1 (conflict-prone).

False positives: Edge and Windows updates legitimately change hashes. Rule: if the new file has a Valid Authenticode signature whose signer equals the pinned signer, log `pin_changed` with `reason=same_signer_update` and re-pin silently; only a signer change, an invalid/missing signature where there was a valid one, or a hash change with an unchanged version string is a finding (`severity=review`, counted, still non-blocking). Signature check without admin: `Get-AuthenticodeSignature` [M: 221 ms in-process, 510 ms via a fresh powershell, msedge.exe status Valid] is too slow to run per launch, so it runs only on a hash MISS (rare: after updates), off the launch path; a `WinVerifyTrust` ctypes call would be faster but is [U] (not measured; no admin needed per its API documentation [A]). Cost is therefore: warm path ~0 ms, update path ~0.2-0.5 s once per updated binary.
