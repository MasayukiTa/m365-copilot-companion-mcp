## 1. Non-destructive reap

Reaper output for a dead coordinator (not a user stop):
- worker `status="interrupted"`, `outcome="INTERRUPTED"`, `reason="coordinator died"`, `resumable=true`, `closed` left as it was (false), `pill` "中断"/color `warn`. Only workers with status NOT in TERMINAL are touched (fixes D1); terminal workers are left byte-identical, merely `closed=true` is not forced.
- status.json top level: `running=false`, `interrupted={"pid","pid_birth","start_ts","detected_ts","last_coordinator_log_ts","coordinator_log","exit_code":null|int,"exit_evidence":[...],"free_bytes_at_death","resumable":true}`.
- `cancelled` stays only for a user stop. Distinguishing rule: a clean stop reaches the coordinator's normal completion path and removes the marker (fleet_runner.py ~2225 comment); the reaper only ever sees marker + dead pid, i.e. never a clean stop. If `commands.json` still holds an unconsumed `stop` command the reaper records `stop_requested=true` and writes `cancelled` (user intent wins) [A: command file layout not re-read].
- Death evidence: pid/pid_birth from the marker; last coordinator log line time = mtime of newest `coordinator_*_p<pid>.log` (name pattern fleet_runner.py:140); exit code: the coordinator is not a child of the supervisor, so no exit code exists for it [V by process tree reading; A that Windows gives none]. For runners the supervisor launched itself, `Register-AutoResumeRunner` already tracks the exit code; otherwise the reap record carries Windows Application-log evidence (Event 1000: faulting module, exception code, matched by pid and time window), read-only via `Get-WinEvent`. Absent evidence is recorded as `[]`, never guessed.
- history.json: non-terminal entries get `status="interrupted"`, `outcome="INTERRUPTED"` (only if `outcome` key exists, as today), `closed` untouched.
- The marker is NOT deleted. It is moved into the snapshot (section 2) and the reaper writes the snapshot BEFORE touching any sidecar; if the snapshot write fails, nothing else is changed (fail closed, retry next cycle). Idempotence: second cycle finds `interrupted` workers and a snapshot with the same pid, no-ops.

## 2. Resume semantics

Authoritative records, by question:
- "Was this goal finished?": `last_run_done.json` (fleet_runner.py:1922-1965), keyed by `jid` else text hash, filled from in-memory workers every snapshot and monotonic (:1965 `_merge_final_done_map`). It covers top-level goals, children and merge goals alike, because any worker with outcome DONE is added. status.json and history.json are DISPLAY, not authority (the reaper rewrites them; "cancelled" in them says nothing about the work). Transcripts (`.fleet/transcripts/r<run>_a<n>_w<k>.jsonl`) are evidence for partial work only.
- "What was the run asked to do?": `last_run_goals.json` (written once at run start) via `_resume_goals` (:1967-2000). Children added by splitting are NOT in it [V: children go through `add_box`, in memory].
- "What did the parent split into?": `.fleet/campaigns.jsonl`: header line (goal, n, cwd, checks, partial) and one line per child (`campaign_id`, `task_id`, `subtask_index`, `text` truncated to 4000 chars) written at split time (relay_fleet.py:8120-8141), read by `campaigns_from_ledger` (fanout.py:479) and `_rehydrate...` (relay_fleet.py:7795-7830). Plus the reaper's snapshot (below), which freezes the plan at death.

Gaps and the changes that close them:
- G1 (FANOUT parent re-run). `_RESUME_SUCCESS_OUTCOMES=("DONE",)` means the FANOUT parent is re-queued on `--resume`; it re-asks the model, reaches `_spawn_children`, finds the campaign on disk and only "adopts" it (relay_fleet.py:8085-8098), costing one turn and queueing nothing. Change: FANOUT counts as resume-done iff its campaign header exists in campaigns.jsonl; without a header (the header write is `try/except: pass`, :8141) the parent is re-queued so work is not lost.
- G2 (unfinished children vanish). On adoption, "children already queued or already done" (comment :8090) is false after a process death: queued children were in memory. Change: at resume, for every campaign with header and no `merge_done`, re-queue each child line whose key (jid, else text hash) is not DONE in the done-map. Child lines gain a `goal` object (full goal dict: cwd, checks, metadata, jid) so the requeue does not depend on the 4000-char `text`; old lines fall back to `text` + header `cwd` (marked `degraded`, logged).
- G3 (merge lost or duplicated). `_note_merged` (relay_fleet.py:8032) writes `{"kind":"merged"}` when the merge is QUEUED, and `_rehydrate` drops `merged` families (:7823). A crash after the queue but before the merge finished loses the answer forever; the reverse (no marker) duplicates it. Change: keep `merged` (compat, meaning queued) and add `{"kind":"merge_done","campaign_id":...}` written when the aggregator worker outcome is DONE. Rehydrate rule: `merge_done` present -> drop; `merged` without `merge_done` and no aggregator DONE in the done-map -> re-issue exactly once (`{"kind":"merge_requeued","attempt":n}`, automatic cap 1); nothing at all -> normal `_queue_ready_merges` (:8165) fires when all children are DONE.
- Exactly-once rule: idempotency key = `campaign_id`; the invariant is "at most one aggregator DONE per campaign_id; a merge goal is issued only when none is DONE and none is currently queued". Residual risk [V from the comment at :8036-8050]: `campaign_id_for` hashes goal text, so an old abandoned unmerged campaign suppresses a fresh run of the same text. The snapshot's `run_start_ts` is stored beside the id so a later change can add an execution id without a format break.

Reaper snapshot: `.fleet/interrupted/<run_id>.json` (run_id = the workers' `r<hex>_a<n>` from status.json `workers[].run_id`, fleet_runner.py:1661; fallback `p<pid>_<start_ts>`), written atomically (tmp + `os.replace`, same helper pattern as fleet_reaper._write_atomic) BEFORE any sidecar mutation. Contents: schema version, the moved marker (pid, pid_birth, start_ts, argv, resume_argv), `interrupted` evidence block, each worker's last state (name, status, outcome, run_id, jid, campaign/role/subtask_index, turns), every campaign plan seen in campaigns.jsonl for this run (header + child keys + merge state), sha1 of last_run_goals.json / last_run_done.json, `resume` block: `{count, last_ts, last_signature, history:[...]}`, and `state: "pending"|"resumed"|"gave_up"|"superseded"`.

Retention exclusion [V by reading fleet_retention.py]: no sweep can touch `.fleet/interrupted/`, by construction and not by luck. `apply` (:1035) runs compress/coordinator_logs/rotations/scratch/stores/workspace_clones/conversations/cap_jsonl. `stores` and `compress` enter only the allow-list `STORE_DIRS=("transcripts","swe")` (:188-200; the doc says allow-list on purpose), `scratch` is non-recursive and matches only root files starting with `_` (:161-179), `coordinator_logs`/`compress` glob only `coordinator_*.log[.gz]` at the root, `rotations` matches `*.log|jsonl.<n>` at the root (:71,:137), `cap_jsonl` lists only root `*.jsonl` (:841). A new subdirectory with `.json` files is outside all of them. Two guards still needed: (a) a test that runs `apply()` on a temp dir containing an old `interrupted/x.json` and asserts it survives with 1-year mtime; (b) the snapshot dir is never named `_*`, `transcripts` or `swe`. Snapshots are removed only by the resumer itself on `state=resumed` completion, or by an explicit owner command. The root-level free-space file is handled in section 3.

Resume entry points:

A new pure `resume_gate(record, now, free_bytes, floor_gb, signature)` returns `(ok, reason)` and holds the loop guard; the PowerShell mirror `Test-FleetShouldAutoResume` (supervisor.ps1:1491) and `scripts/test_supervisor_fleet_resume_guard.py` are extended in lockstep.

## 3. Free-space observability (value independent)

Everything below only REPORTS. No threshold, default, or floor value is added or changed; `disk_floor_gb` remains the owner's setting and is only read (`settings_disk_floor`, fleet_runner.py:1026; `operator_set_a_disk_floor`, :1037, tells "unset" from "0").
- Existing facts [V]: `_snapshot` already emits `free_disk_gb` and `disk_floor_gb` (fleet_runner.py:1585-1586) from `free_disk_gb()` (relay_fleet.py:2327), which returns 1e6 on error. That answers "was there a reading" but only in the latest snapshot, which vanishes at death.
- `.fleet/free_space.jsonl`: one record every 30 s (piggybacked on the existing status write cadence, whichever is slower), `{ts, pid, free_bytes, total_bytes, drive, floor_gb|null}`. Implementation: a FIXED-SIZE ring of 256 slots x 128 bytes (32 KB) created and zero-filled once at coordinator start, file handle kept open for the process lifetime, each sample overwrites slot `n % 256` in place with a space-padded JSON line and no `flush`-triggered growth. Because the bytes are pre-allocated, a full disk cannot make the write fatal (no new cluster is allocated); all writes are `try/except` and count failures into a status field. This replaces rotation with a hard cap by construction. Reader (`fleet_diag`) sorts by `ts`. `cap_jsonl` (retention :841) only trims files above 64 MB so a 32 KB file is never touched; if the name clashes with future rules, use `.json`.
- Surface: status.json gets `disk: {free_bytes, floor_gb|null, below_floor: bool|null, sampled_ts, log_failures}` where `below_floor` is `null` when the floor is unset/0 and otherwise the plain comparison `free_gb < floor_gb`. The cockpit health strip (`_healthDot`, FleetCockpit.cs:1163, `BuildHealthStrip` :2420) tints the disk dot from `below_floor==true` (warning) and shows the numbers in the tooltip; the dot uses no new color threshold. The interrupted card shows `free_bytes_at_death`.
- Top consumers on demand only: `python -m relay.fleet_diag disk --top 15` (new small module) measures the top directories of the drive (`.fleet` subdirs, temp, HF/pip caches named in the tree) and writes one telemetry row; a cockpit button and the supervisor's pre-resume gate may invoke it, nothing schedules it (a scan of a full disk is itself heavy and must not run in the loop).
- Crash forensics: `faulthandler` is installed only for the MCP server (main.py:1253-1290) [V grep: no use in relay/]. The coordinator gets `faulthandler.enable(file=fh)` to `.fleet/fault_p<pid>.log`, a 64 KB file pre-zero-filled at start and kept open (same no-allocation reasoning). Name deliberately not `coordinator_*.log` (it would enter `coordinator_logs`' keep-20 window, retention :114) and not `*.log.N`; old ones are pruned by the resumer after they are copied into a snapshot. 0xC0000006 is an in-page error on an mmapped sqlite `-shm` [V from the incident; A that a pre-touched fault log is written by faulthandler's C handler on that path]; the design goal is only that a native crash leaves a trace, and this must be tested by a deliberate `faulthandler._sigsegv()` in a child process. The exit code goes into the reap record as in section 1 (only when known).

## 4. Supervisor pre-resume gate

Before `Invoke-FleetAutoResume` launches, a new `Get-FleetResumeCrashGate` (PowerShell, mirrored by the Python pure function `resume_gate`) collects: free bytes now (`[IO.DriveInfo]` of the `.fleet` drive); the crash signature = sha1 of (exception code | faulting module | error class), from (a) the last 200 lines of the newest `coordinator_*.log` looking for the fixed marker strings `No space left`, `WinError 112`, `Errno 28`, `database or disk is full`, `disk I/O error`, (b) the Windows Application event for the dead pid, (c) `interrupted` evidence from the snapshot; and the owner's floor (read only). Decision, with no policy value invented:
- if the current signature equals the previous attempt's signature (`resume.last_signature`) AND free bytes now are not greater than at the previous death, refuse;
- if the owner's floor is set (>0) and free < floor, refuse and say so (reads the setting, does not decide it);
- if ENOSPC-class evidence is present and free bytes did not increase since death, refuse;
- otherwise proceed, still under the count/backoff guard.
A refusal writes `state` unchanged plus `resume.blocked={reason, ts, free_bytes, signature}` in the snapshot, `Write-Log`, and surfaces in status.json `interrupted.blocked_reason` (the card and health strip read it). Whether a minimum free space is required to resume at all is a policy question left to the owner (open question 1).

## 5. Fan-out parent state

Facts [V]: the parent is ended `done/FANOUT` at relay_fleet.py:5924 on purpose (a parent parked until children finish holds an admission slot and deadlocks when concurrency < children; comment :5915). `done_count`/`running` in `_snapshot` (fleet_runner.py:1558-1573, `queued` keeps `running` true) and the loop `any(w.status not in TERMINAL)` (relay_fleet.py:8398) rely on that terminal status.

Options:
- A. Change the status to `awaiting_children` (non-terminal). It would need the parent to be excluded from admission occupancy, the sweep-loop exit test (:8398), `done_count`, `_unfinished()`, TERMINAL-based closing (tab close at finish, :8735/:8805), plus every C# copy of the terminal list, and a rewrite to `done` at merge time from a different thread of control. Every one of those sites is a chance to reintroduce the deadlock this design exists to avoid. Rejected.
- B (recommended). Keep `status="done"`, `outcome="FANOUT"` byte for byte and add a separate DISPLAY field computed only in snapshot builders: `display_state` in {`awaiting_children`, `merging`, `done`, `merge_failed`, `interrupted`} plus `children_done`/`children_total`, computed from `fanout_family_view` (fanout.py:754; already called in `_snapshot` and at run end fleet_runner.py:4489). Rules: unmerged campaign and any child not terminal -> `awaiting_children`; all children terminal, aggregator queued/running -> `merging`; aggregator DONE (the `merge_done` line of section 2) -> `done`; aggregator STUCK/ERROR after its retry cap -> `merge_failed`; run reaped -> `interrupted`. The parent becomes "done" for display exactly when the merge goal's result is DONE. The cockpit paints the pill from `display_state` when present and falls back to `status` for old files; TERMINAL logic keeps reading `status`, so archive/retry/counters are unchanged. Change sites: `fanout_family_view` result gains the fields; `_snapshot`/`_final_worker_entry` (fleet_runner.py:1650-1665, 4436) copy them; FleetCockpit.cs `StatusLabel` and card pill read `display_state` first; Theme.cs labels "子タスク待ち"/"Awaiting children", "統合中"/"Merging".
- Accounting effects [V unless marked]: refuter and `checks`: the parent's checks already move to the merge (relay_fleet.py comment ~5904), so the parent has none to run; nothing changes. `done_count`: FANOUT is already "done" via `report_status` (fleet_runner.py:4478); unchanged. Telemetry: the `fanout` mechanism row (relay_fleet.py:8150) is unchanged; a `fanout_merge` row (campaign_id, children, elapsed) is added at `merge_done`. Effort bench (docs/private/20260930_effort_bench_design.md:64): the bench's outcome is the grader verdict on the diff and cost is the sum of history rows joined by the `wt_<inst>` path, so history rows keep `status done / outcome FANOUT` unchanged and `display_state` must not be read by the bench (added to the bench doc's "do not read" list in a follow-up). Option A would have changed those history rows and invalidated the "FANOUT parent is not a solve and not a failure" rule.
