## 2026-11-12 - The pipe-drain thread survives a failed host-log write

- Change: RotatingLog.write_line (relay/tunnel_host_log.py) no longer lets a file error escape. A tell/rotate/write/flush OSError (e.g. ENOSPC) is caught: the line is dropped and counted, the handle invalidated and reopened at most once every 30s (REOPEN_THROTTLE_SECONDS) while the fault persists. On the first successful write after a failure streak, one (N lines dropped while the log could not be written) notice is written (normal millis_stamp format) and the counter resets. _open() no longer raises on a failed (re)open, and a failed initial open still constructs the object. pump_stream wraps sink.write_line/on_line and reads to EOF regardless of per-line failures -- draining the host stdout/stderr pipe is the first priority.
- Behaviour: reproduces and fixes the silent-host incident -- the host log stopped mid stack-trace at 2026-11-12 18:41:35 and was silent for hours while the reader (pid 24664) and its devtunnel host child (pid 32472) stayed alive. Root cause was the one unguarded self._fh.write(...): an OSError there unwound out of pump_stream read loop and killed the pump thread; with nobody draining the pipes the host blocked on write (same structure as the 2026-10-31 incident noted at the top of the module).
- Tests: relay/test_tunnel_host_log.py (hermetic, no Windows-only paths) with an OSError-raising fake file object and an injected clock: write_line never raises; pump_stream drains a 100-line stream to EOF while every write fails; exactly one dropped-notice precedes the first recovered line; the reopen is throttled to once per 30s; a failed initial open still constructs. Full file: 28 passed.
- Open: the reopen throttle is time-based (30s), not backed by a free-space probe, so on a persistently full disk the reader keeps draining and dropping (by design) until space returns; no alerting is wired beyond the dropped-line notice in the log itself.
