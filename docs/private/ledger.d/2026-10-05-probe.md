## 2026-10-05 - The bridge tool-call probe is a fallback, not a schedule

- Problem. `bridge/copilot_bridge.py:_run_tool_probe` sent a real Copilot message every 10 minutes
  (`MCP_TOOL_PROBE_SEC`, default 600) into one persistent conversation: 118-158 messages on full days
  (9/28-10/4, `.fleet/tool_events.jsonl` rows with `probe_challenge`), 43-81 distinct MCP sessions a
  day. Copilot Studio counts sessions, so the probe is overhead in the owner's conversation
  analytics. Measured on the same ledger: 35-48 % of probes were sent within 30 min of a REAL,
  non-probe tool call (41/118, 71/148, 74/158, 50/139 on the four full days), i.e. after the thing the
  probe proves had already been proved for free. A failed probe also led to a quick re-probe and,
  after a streak, a conversation recycle (another session each).
- Change.
  1. Skip while a real call proves the path. Before sending, the bridge asks
     `tools/fleet_tool_health.py:last_real_success(now, interval_s)`: the newest ledger call within the
     interval whose outcome succeeded (`row_ok`, not `row_unavailable`), is not discovery chatter
     (`call_tool.*`) and is not a probe call (arguments name `probe_challenge`). If there is one, no
     message is sent and `tools/tool_probe.py:record_evidence` writes the health record
     (`.fleet/tool_probe.json`) as ok, kind "answer", `evidence: "real_call"`, at THAT CALL'S OWN
     timestamp (never `now`), never moving the record backwards, totals untouched (nothing was
     probed). No ledger / no such call = no evidence = the probe runs.
  2. Idle cadence = setting `tool_probe_idle_min`, default 30, choices off(0)/15/30/60 (hand-edited
     5..1440 is honoured). Decided from the data: replaying the ledger (a probe is due when neither a
     probe nor a real call proved the path for N minutes) gives 96-137 probes/day at N=10, 61-91 at 15,
     28-44 at 30, 12-21 at 60. 30 was chosen because (a) the cockpit's Tool dot used to go red after
     20 minutes without a record, so it had to move with the interval anyway and 30 keeps the stale
     limit (interval + 10 = 40 min) small enough to still mean "the prober has stopped", and (b) 15
     still leaves ~65 messages a day while 60 doubles the blind window for a bridge-only failure on an
     idle machine. 0 = never probe: the check shows "not checked" (grey), never green.
     `MCP_TOOL_PROBE_SEC` stays as the env override of last resort: when set it wins over the
     setting exactly as before (seconds, <=0 disables) and is shown as such on the screen.
  3. Failed probe -> back off. Wait = interval x 2^consecutive_failures, capped at 2 h
     (`tool_probe.backoff_s`, applied in `_probe_due_at`); a probe turn that never ran (empty reply in
     <5 s) now retries 30 s, 60 s, 120 s... never beyond the interval instead of a fixed 30 s forever.
     One `tool_probe_backoff` row per backed-off probe in `.fleet/mechanisms.jsonl`
     (relay/mechanism_telemetry.py). The existing stuck-conversation recycle (N consecutive failures)
     is unchanged but now needs far fewer messages to be reached.
  4. State export, additive. Bridge `/status` (open route) gets
     `probe: {enabled, interval_min, source, last_sent, last_skipped_reason, last_skipped_ts,
     skipped_since_start, evidence_ts, evidence_tool, backoff_failures, next_due}`; the same dict is
     written (change-only, atomic, single writer) to `.fleet/tool_probe_state.json`, a separate file
     from `tool_probe.json` because `record_probe` replaces that file whole. status.json is not
     involved (the coordinator does not read the probe).
  5. GUI. Cockpit gear popup, section `Recovery / 復旧` (under auto-resume): select
     "Tool-call check interval (idle) / ツール呼び出し確認の間隔(待機時)" off/15/30/60, SaveKey only,
     no-refire paint guard, junk value keeps the value, an "in effect" line from the state file
     (interval, last sent, skipped count, last skip reason, backoff) and a pending note while the
     bridge still reports another interval. Words in `ToolProbeView` (ui/EffortPolicy.cs). No header
     control. The Tool dot's stale limit follows the interval (`ToolProbeView.StaleAfterMin`) and the
     dot is grey when the bridge reports the probe off.
- Dependents of the old fixed 10 min, fixed in the same change (each would otherwise have turned a
  slower probe into a regression): `relay/relay_fleet.py` CONNECTOR_PROOF_WINDOW_S was 2 x 600 s and
  only read the probe's own stamp, so a busy machine (no probes now) would have read as "connector not
  proven" and filed INFRA_STUCK; it now follows `tool_probe.configured_interval_s()` and also accepts
  a real successful call (source "call"). `relay/copilot_autopilot_relay.py`
  STUCK_TOOL_HEALTH_MAX_AGE_S (1800) is now max(1800, 3 x interval).
- What changed against the old behaviour (golden). The FIRST probe after bridge start is unchanged:
  30 s startup delay, due immediately because nothing was sent. Different: 30 min instead of 10
  between idle probes; none at all while a real call succeeded within the interval; longer waits
  after failures.
- Expected effect. From the replay above: about 100-140 -> 28-44 probe messages/day (about -65 to
  -75 %) and proportionally fewer probe-only sessions (43-81/day measured); more on days with a busy
  fleet, less saving on a fully idle day (48/day at 30 min, 24 at 60).
- Limits, stated plainly. (a) Evidence is any successful non-probe call the gateway ledgered; the
  ledger cannot tell a Copilot call from another MCP client's (96 % of rows are unattributed), so a
  Copilot-connector-only outage while another client keeps calling would not be caught until the
  interval passes with no calls. That is the price of "never ask Copilot when we already know".
  (b) The bridge-only failure mode on an idle machine is now found within 30-40 min instead of 10-20.
  (c) Setting changes are noticed within about 5 minutes (the timer polls), a probe in flight is not
  interrupted. (d) Not run on the live bridge; behaviour verified with stubs, the cockpit by
  `bench/ui_build_check` and source-shape tests.
- Operator note. `MCP_TOOL_PROBE_SEC` (env, seconds) overrides the setting and disables the probe at
  <=0; documented here as the last resort. `.env.example` line updated.
- Tests. `tools/test_tool_probe_skips_when_the_fleet_proves_it.py` (skip on recent real call, send
  when idle, own call is not evidence, never green without an event, setting 0, env override, backoff
  and mechanism row, empty-turn backoff, timer tick deferral, /status field, GUI shape);
  `tools/test_a_setting_declares_when_it_takes_effect.py` (new reader); `relay/test_stuck_tool_health.py`
  (threshold now derived).
